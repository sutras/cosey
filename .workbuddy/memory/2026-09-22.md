### 1. 列定义收敛（P1-1/2，根因）

- 新增 `pruneColumns()`（`utils/excel/index.ts`，已导出）：丢掉非对象项（`false`/`null`/`undefined`），
  并递归丢弃「子列被剔光」的组。

  `flatColumns()`（数据行）与 `columns2aoa()`（表头）；`noGroup` 分支仍走 `columns2lastLevelAoa(fColumns)`。
- 触发场景：组件 `table-export` 的 `transformColumns` 在分组列的子列全被取消勾选时会产出
  `{ label: 'G', columns: [] }`；以及 `MayBeTableColumnProps` 明确允许的 `false`/`null`。

### 2. 入参校验（P1-3）

- `worksheets` 为空 → 抛「需要提供 worksheet 或 worksheets」（此前 xlsx 会生成一个 0 个工作表的工作簿）。
- `data[name]` 不是数组 → 抛「找不到工作表「x」的数据…」（此前 csv/txt 报 `reading 'sheet'` 之类 TypeError）。
- `bookFormats.ts` 新增 `getBookFormat()`，`getExtByBookType` / `getMimeByBookType` 不再用 `find(...)!`，
  bookType 非法时抛「不支持的导出格式：pdf」。
- `filename` 已带正确扩展名时不再重复拼接（`报表.xlsx` 不再变 `报表.xlsx.xlsx`）。

### 3. csv/txt 公式注入（P1-4）

- `csv.ts` 新增导出的 `escapeFormula()`：`= + - @ \t \r` 开头的值前置单引号；
  纯数字形态（`-42.5` / `+7` / `1e3`）放过，避免把正常负数写成文本。
- 顺手修 `aoa2csv`：不再用 `new RegExp(`[${FS}"\n]`)` 拼字符类（FS 传 `]` 会 SyntaxError），
  改成 `value.includes(FS) || /["\n\r]/`，孤立的 `\r` 现在也会被引号包住。

### 列宽可行性结论（Tiny 问，未实施）

- 现状：**xlsx 不支持设置列宽**。`xlsx.ts` 里 sheet XML 只有一句
  `<sheetFormatPr defaultColWidth="10.3846153846154" defaultRowHeight="16.8" />`，全表一个默认值，
  没有 `<cols>` 节。
- 断点不在序列化层而在 `exportExcel`：`columns` 的宽度信息其实一直是活的
  （`TableColumnProps` 派生自 element-plus 的 `elTableColumnProps`，自带 `width`/`minWidth`；
  `table-export.transformColumns` 又是 `...column` 全量透传），
  但 `aoa2sheet(name, aoa)` 只把二维数组收成 `Cell[][]`，`WorkSheet` 只有
  `name / sheet / headRowCount` 三个字段 —— 列定义过了这一跳就没了，`wb2xlsx` 拿不到列，自然写不出宽度。
- 要加的话动 3 处：① `WorkSheet` 加列宽字段，`exportExcel` 在 `aoa2sheet` 后回填修剪后的 `fColumns`；
  ② `wb2xlsx` 在 `<sheetFormatPr>` 之后、`<sheetData>` 之前插 `<cols>`（OOXML 子元素顺序是强制的）；
  ③ 定「用哪个字段 + 单位换算」：element-plus 的 `width` 是 px，Excel 的 width 是「默认字体下数字 0 的字符数」，
  96dpi 下约 `px = width * 7 + 5`，但这份 styles.xml 默认字体是宋体 11、中文占约 2 个字符宽，
  纯中文表头直接套公式会偏窄 —— 倾向加独立字段（字符数语义），而不是复用 px 的 `width`。

### SheetJS（npm `xlsx`）的列宽约定（调研结论）

装了 0.18.5 到隔离 node workspace 读源码 + 跑探针实测（源码位置：
`node_modules/xlsx/xlsx.js:10015` 换算函数、`:14406` `col_obj_w`、`:14707` `write_ws_xml_cols`、`:15072` 挂载点）。

- 入口是 `ws['!cols']`，**0-based 下标**（Excel 的 C 列 = 下标 2 = `decode_col('C')`）；
  数组**允许有洞**，写的时候 `if(!(col = cols[i])) continue` 直接跳过那一列。
- 三种宽度字段（都在同一个 `MDW` 基准上）：
  `wch` = 内容区字符数（Excel 工具提示/UI 显示的就是它）；
  `width` = 外宽 = `wch + 5/MDW`，**这个才是写进 XML `width` 属性的值**；
  `wpx` = 屏幕像素。换算：`char2width(c) = round((c*MDW+5)/MDW*256)/256`、
  `px2char(px) = floor((px-5)/MDW*100+0.5)/100`、`width2px(w) = floor((w + round(128/MDW)/256)*MDW)`。
  标准默认列 8.43 字符 / MDW 7 → width 9.14 → 64px。
- `hidden`、`level`（0–7，Excel UI 显示 1–8）也走同一对象；分组折叠按钮位置在
  `ws['!outline'].left`。全套还要求读写都传 `cellStyles: true`（0.18.5 实测不传也能写）。
- 产出的 XML：每个下标一条 `<col min="n" max="n" width="…" customWidth="1"/>`，
  `hidden="true"` / `level="1" outlineLevel="1"` 按需附加。位置在
  `sheetFormatPr` **之后**、`sheetData` **之前**（源码 15059–15074 的写入顺序：
  sheetPr → dimension → sheetViews → sheetFormatPr → cols → sheetData），与之前的判断一致。
- 三个坑：
  ① 写入端 `DEF_MDW = 6`（不是 7）—— `{wch: 8.43}` 实测出来是 `width="9.26171875"`；
  要精确得显式给 `MDW: 7`（实测 `{wch:12, MDW:7}` → `12.71484375` ✓）。
  ② 给了 `width` 就**原样写出不做换算**，和 `wch` 混用会不自洽（实测 `{width:20}` → `width="20"`）。
  ③ 读回来是**有损的**：解析时用 `find_mdw_colw` 猜 MDW，实测写 `wch: 8.43` 读回 `wch: 8.63`。
- MDW 只以「数字 0」的宽度为基准，**中文字符不参与**，所以 SheetJS 也帮不了中文列 ——
  中文按 2 个 MDW 估算得自己加。Excel 自己的「自动调整列宽」是字体测量，不走这套公式。
- 对照：exceljs 是 `worksheet.columns = [{ header, key, width }]`，语义等价于 `wch`（内宽字符数）。
