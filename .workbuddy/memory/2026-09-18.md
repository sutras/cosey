## packages/cosey 的 co:\* 图标迁到 richtext-icons 组件

**背景**：`packages/cosey` 里 62 处 `<Icon name="co:xxx" />` 用法（44 个文件）全部改为
import `richtext-icons` 导出的 `Rti*` 组件。

**依赖**：`packages/cosey/package.json` 的 `dependencies` + `devDependencies` 加
`richtext-icons@^0.1.0`（纯 ESM，`exports` 只有 `import` 条件）。`pnpm-lock.yaml` 在本仓库是
gitignore 的，不进版本库。

**核心手法（可复用）**：

- 静态字面量走脚本批量替换：正则匹配 `<Icon|co-icon ...name="co:x"... />`，删掉 name 属性、
  把开标签压平、自闭合改写成 `<Icon ...><RtiX /></Icon>`，再在 import 块末尾插一行
  `import { ... } from 'richtext-icons';`，最后用 `npx prettier --write` 收尾。
  脚本备了一份在 `/tmp/rti-migrate.py`（含 co→Rti 映射表）。
- 保留 `<Icon>` 外壳（改用默认插槽放 Rti 组件）是最省事的做法：`icon.tsx` 的 slot 分支渲染的
  `co-icon co-icon--size` 内层 span 与原来结构完全一致，`size` / `class` 语义和 CSS 钩子都不动。
- 5 个 format 子组件（format-mark / -list / -indent / -align / -size-delta）的 `icon` prop 从
  `String` 改成 `Component`（`[Object, Function]` + `PropType<Component>`），用 `h(props.icon)` 渲染。
- `ContextMenuItem` / `ContextSubMenu` / `Content` 的 `icon` prop 保持**向后兼容**，改成
  `String | Component` 联合类型，渲染时按 `isString` 分支。
- `useColorScheme.ts` 的 `ColorSchemeOption.icon` 由 `string` 改为 `Component`（仓库内无消费方）。

**语义映射里的几个判断题**（不是字面直译）：
`co:table`→`RtiTableInsert`（按钮动作是插入表格）、`co:eyebrow`… 准确说
`co:eyedropper`→`RtiColorPicker`、`co:video-player`→`RtiVideo`、
`co:ibm-watson-language-translator`→`RtiTranslate`、`co:trash-can`→`RtiDelete`、
`co:add-large`→`RtiPlus`、`co:close-large`→`RtiClose`、`co:code`→`RtiInlineCode`；
content-table 工具条里原本拿 chevron 凑的「上移行/下移行/左移列/右移列」改用图标库专门的
`RtiRowMoveUp` / `RtiRowMoveDown` / `RtiColumnMoveLeft` / `RtiColumnMoveRight`。

**验证**：`vue-tsc -p tsconfig.app.json` 在 `packages/` 下 0 错误；`eslint --max-warnings 0`
通过；`vite build` 成功；脚本校验 79 个 `Rti*` 引用全部存在且图形非空；用 `vite preview` +
agent-browser 登录 mock（`admin` / `123456`）实际看了登录页、主壳、富文本编辑器工具条，
图标渲染与尺寸正常。

**踩到的坑**：

1. `pnpm install` 要写 `~/Library/pnpm/store`，在沙箱里会被拦（`ERR_PNPM_EPERM`），
   需要以提权方式跑；后台任务不会弹授权，得放前台。
2. 根目录 `prepare` 钩子（husky）会失败：它要删 `.husky/_/husky.sh`，被 WorkBuddy 的
   safe-delete shim 挡住。属于环境问题，不影响依赖安装结果。
3. **同一条消息里对同一个文件并发发多个 Edit 会丢更新**（在 `table-column-editor/item.vue`
   上丢了一次）。同一文件的多处修改要串行。
4. `vue-tsc` 在 `src/views/**` 有 6 个既有错误（`FieldSelectOption` / `CheckboxOption` 类型），
   与本次改动无关；`pnpm build` 因此本来就会失败，验证时用 `npx vite build` 跳过 `vue-tsc`。

**遗留**：`lib-dist/cosey`（gitignore）还是旧构建，docs 包通过 `file:../lib-dist/cosey` 消费它，
需要时跑 `pnpm cosey:build` 重新生成。`src/` 与 `docs/` 里没有 `co:` 引用（菜单用的是
`bi:` 前缀的 bootstrap-icons），未受影响。

## 编辑器工具栏分组/排序评审（只评审，未改代码）

**实测环境**：`docs` dev server（`localhost:5174`）的 editor 页，用 agent-browser `eval` 量盒子。
注意工具栏 element 类名是 `co-editor__toolbar`（BEM 元素用双下划线），不是 `co-editor-toolbar`。

**实测数据（关键）**：

- 11 个分组，各组宽之和 1160px，加 10 个 `column-gap: 24px` ≈ **1400px**；容器要 ≈1430px 才排成一行。
- docs 页容器 549px（工具条内容区 523px）→ **3 行**；700px 仍 3 行；900/1100/1300px → 2 行；420px → 4 行。
  → 任何真实布局都至少 2 行。
- 行首 top 实测 1372 / 1404 / 1438 → 行间距 **32 / 34 不匀**。原因：颜色/背景用的 `ButtonSplit`
  有 `border: 1px solid transparent`，盒高 **30px**，其余按钮 28px；`__group-list` 是
  `align-items: normal`(stretch) 而 `__group` 是 `height: fit-content`，所以 30px 的组不被拉伸、
  顶部对齐、把该行撑高 2px。
- 最宽的原子组 = `[FormatHeading][FormatFont][FormatSize]`（3 个 100px Select + 2 个 28px 按钮
  = 364px）。容器 < ~390px 时这组**自己内部折行**（实测 360/320/280 下组内 2 行）。

**结论（评审意见）**：分组与排序的大方向与 Word / Google Docs / 飞书 一致
（段落样式 → 字体字号 → B I U S → 颜色 → 列表 → 缩进 → 对齐 → 引用/代码 → 插入 → 清除 → 源码），
顺序不需要大改。该改的是三处：

1. `[FormatBlockQuote][FormatMark code]` 这组内容不纯：引用是块级、行内代码是字符级；
   且同族的 `行内代码` 与 `FormatCodeBlock` 被拆到第 8、9 两组。
2. `[B I U S]` 与 `[上下标]` 拆成两组 → 549px 下折行正好把这对同族切到两行。
   合并成 1 组（7 项 ≈ 202px）可让折行不再切断同族。注意**分组在这里同时是折行的原子**，
   所以"分组细 = 折行灵活、语义散"是一对权衡。
3. 缺 **撤销/重做** 按钮：`pm/plugins.ts` 已 `history()`，keymap 已绑 `Mod-z` / `Mod-y`，
   facade 也有 `exec(command)`，只是工具栏没入口。

**建议的 10 组方案**（3 个语义带）：
文字格式 `[撤销 重做] [段落样式 字体 字号] [B I U S 上下标 行内代码] [颜色 背景]`；
段落格式 `[列表] [缩进 对齐] [引用 代码块]`；
插入与工具 `[链接 图片 视频 表格 公式] [清除格式] [源码]`。

### 追加：工具栏分组/排序的信息架构评审（用户明确不关心折行，只看功能分组与排序）

**关键发现：`editor.tsx` 的分组几乎逐条照搬 Quill 的默认 `toolbarOptions`**（Quill 官方文档
quilljs.com/docs/modules/toolbar）。11 组里 8 组能一一对上：
`[B I U S]`=`['bold','italic','underline','strike']`、`[上下标]`=`[{script:sub},{script:super}]`、
`[颜色 背景]`=`[{color},{background}]`、`[有序 无序]`=`[{list:ordered},{list:bullet}]`、
`[缩进±]`=`[{indent:-1},{indent:+1}]`、`[对齐×4]`=`[{align:[]}]`、
`[链接…公式]`=`['link','image','video','formula']`（项目自加 table/code-block）、`[清除格式]`=`['clean']`。
但**排序被重新编成了 Word 那一系的"文字处理器序"**，而不是 Quill 那个"全开演示序"。这个组合是对的。

**行业顺序（已联网核实）**：

- Word 字体组：字体名→字号→增减字号→B I U S→删除线→下标→上标→突出显示→字体颜色→**清除所有格式**；
  段落组：项目符号→编号→多级列表→减少/增加缩进→对齐→行距。→ 即 `列表 → 缩进 → 对齐`。
- Google Docs：撤销/重做→样式→字体→字号→B I U→文字颜色/高亮→插入链接/评论/图片→**对齐→行距→列表→缩进→清除格式**。
- TinyMCE 核心默认：`undo redo | styleselect | bold italic | alignleft aligncenter alignright alignjustify | outdent indent`；
  官方 WP 配方：`undo redo print spellcheckdialog formatpainter | blocks fontfamily fontsize | bold italic underline forecolor backcolor | link image | alignleft…justify lineheight | checklist bullist numlist indent outdent | removeformat`。
- 结论：**列表/缩进/对齐 三者的内部顺序行业不统一**——Word 是「列表→缩进→对齐」，
  GDocs/TinyMCE 是「对齐→列表→缩进」。项目取的是 Word 序，合理。
  **清除格式**：Word 放在「字体」组内（末尾），GDocs/TinyMCE 放工具栏末尾 —— 项目放末尾，也合理。

**三处偏差（评审结论）**：

1. **缺「撤销/重做」**（唯一实打实的缺失）。`pm/plugins.ts` 已 `history()`，keymap 已绑
   `Mod-z`/`Mod-y`，facade 有 `exec(command)` —— 只差按钮。行业恒在最左。
2. **第 8 组 `[FormatBlockQuote][FormatMark code]` 跨维度混组**：引用是块级、行内代码是字符级；
   Quill 原组是 `['blockquote','code-block']`，这里把 code-block 换成了 inline code，
   于是「行内代码」与「代码块」被拆进第 8、9 两组。**唯一一处真正的分组错误。**
3. **第 1 组 `[段落样式][字体][字号]` 把块级控件和字符级控件并入一组**。Quill 里
   header / size / font 是三个独立组，Word / GDocs 也分开。属于"视觉上并排可以、同组牵强"，
   可改可不改（权衡项）。

**注意**：`上下标` 独立成组**不算问题** —— Quill 默认也是独立一组；只是 Word/GDocs 把它归在字符格式簇。
`源码` 放最末、`清除格式` 放末尾都与 TinyMCE / GDocs 一致。
